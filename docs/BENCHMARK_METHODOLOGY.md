# Benchmark Methodology

**Status:** draft 1, 2026-07-31. Planning only; no implementation.
**Depends on:** `docs/PRD.md` (this repo), `BENCHMARKS.md` and `CLAIMS_AUDIT.md` in `../llm_inference_engine`.

This is a first-class deliverable, not an appendix. Serving-systems projects fail at the benchmark, not at the code: the code is usually fine and the numbers usually cannot survive three follow-up questions. This document exists so that every number this project publishes has a stated generating process, a stated baseline, and a stated failure mode.

The standard to match and exceed is the engine's own `BENCHMARKS.md`, which does several things right: declares batch-1 scope at `:19`, publishes the row where its kernel *loses* at `:94`, names its own unmeasured splits at `:151`, keeps a known-gaps list at `:243-250`, and **commits its result artifacts** — 24 files under `bench/results/`, tracked in git.

> **Correction, 2026-07-31.** Earlier drafts of this document cited `CLAIMS_AUDIT.md:6` (*"`git ls-files` returns zero result files"*) as the engine's one real failure. **That audit is stale and the claim is false.** The engine committed its artifacts in commit `c24afaf`; `git ls-files bench/results/ | wc -l` returns 24, and `.gitignore:29` records the decision explicitly. This document inherits that standard rather than correcting a failure.

## 1. The load-generation model: open loop, and why it changes the numbers

### The distinction

**Closed loop:** a fixed number of clients, each of which sends a request, waits for the full response, then sends the next. Offered load is a function of system speed — if the system slows down, clients send less. Concurrency is capped at the client count by construction.

**Open loop:** requests arrive on a schedule independent of the system. If the system slows down, arrivals keep coming and the queue grows. Offered load is a parameter you set, not an outcome.

### Why this is the single most important choice in this document

A closed-loop harness **cannot measure queueing delay**, because it cannot create a queue deeper than its client count. Under a closed loop, latency degrades gracefully and monotonically, and the system appears to have no saturation point — the numbers get slowly worse forever and never fall off a cliff. Under an open loop, the same system shows a knee: below capacity, latency is flat and dominated by service time; above capacity, queue depth grows without bound and latency diverges. **The knee is the interesting result and closed-loop testing hides it.**

This is precisely the trap that makes serving benchmarks indefensible. A closed-loop p99 at 32 clients is a statement about 32 clients, not about the system. It is not comparable to anyone else's number, and it will be dismissed by anyone who has built a serving system.

**The engine's existing harness is strictly closed-loop with one client and zero think time.** `bench/harness.py:156-180` is a nested `for prompt` × `for run`; `:106-139` consumes one generator to completion. There is no arrival process, no queue, no concurrency, no HTTP client at all (`CLAIMS_AUDIT.md:259`). It is a correct microbenchmark for batch-1 decode speed and it is structurally incapable of measuring anything this project claims. **It is reused for components, not as a harness** — see §9.

### Commitment

**Primary results are open-loop.** Requests are generated by an arrival process at a configured rate, submitted regardless of outstanding work, over real HTTP with SSE parsing. Closed-loop runs are permitted only as a labeled secondary result, for the specific purpose of measuring per-request service time in isolation, and must be labeled `closed-loop, N clients` wherever they appear.

**Client-side coordinated omission must be avoided.** If the load generator is at all synchronous — a shared client that blocks — then when the server stalls, the generator stops issuing requests that *should* have been issued, and those slow requests never appear in the latency distribution. This makes a saturated system look fast. Mitigation: latency is measured from the **intended dispatch time** derived from the arrival schedule, not from actual send time. Where actual send time drifts from intended send time, the drift is recorded and reported as a harness health metric; if drift exceeds a threshold, the run is invalid and is discarded, not published.

**[inference]** Coordinated omission is the single most likely way this project publishes a wrong number without noticing. It goes in the risk register as a *silent* invalidator.

## 2. Metrics: definitions before measurement

Every term is defined here so that no result is ambiguous about what was timed.

| Metric | Definition | Notes |
|---|---|---|
| **TTFT** — time to first token | Intended dispatch time → arrival of the first SSE chunk containing non-empty `delta.content` | Includes queue wait, admission delay, prefill, and first-token detokenization. This is the metric prefix caching and routing move. |
| **ITL** — inter-token latency | Wall time between consecutive non-empty content chunks for a single request | Per-request series; pooled across requests for percentiles. |
| **TPOT** — time per output token | Mean ITL for a request = (end − first token) / (output tokens − 1) | One scalar per request. Reported alongside ITL percentiles, not instead of them. |
| **E2E latency** | Intended dispatch → final chunk (`finish_reason` set) | The metric a user experiences. |
| **Queue wait** | Intended dispatch → admission into a running batch | Server-side instrumented. The difference between E2E and service time. |
| **Throughput** | Output tokens/sec summed across all concurrent requests, over the steady-state window | Not the headline. |
| **Goodput under SLO** | Completed requests/sec **that met the SLO**, over the steady-state window | The headline. §3. |
| **Cache hit rate** | Cached blocks reused / total blocks required at prefill, per request, aggregated | Block granularity, not token or request granularity. §7. |
| **Preemption rate** | Preemption events / decode iterations | With recompute-vs-swap broken out separately. |
| **Offered load** | Configured arrival rate (req/s), a parameter | Distinct from achieved throughput. Reporting one as the other is a classic error. |

Two definitional traps, called out because they are common and quiet:

- **A "first token" that is an empty string is not a first token.** The engine's server emits a chunk per token id and detokenizes with `skip_special_tokens=True` (`engine/server.py:70`), so leading special tokens produce chunks with empty `content`. Timing TTFT to the first *chunk* rather than the first *visible content* would understate TTFT. Fixed by definition above.
- **Prefill tokens are not output tokens.** Throughput must state which it counts. This project reports **output tokens/sec** as throughput and reports prefill token throughput separately; a combined "total token throughput" number is not published, because it can be inflated arbitrarily by lengthening prompts.

## 3. Goodput under SLO as the primary metric

### The argument

Raw throughput is trivially gameable: batch harder, tolerate worse latency, throughput goes up. A serving system that achieves high tok/s while every request violates its latency target has served no one. Conversely, a latency-only metric ignores that the system exists to do volume.

**Goodput** — the rate of requests completing *within* an SLO — is the metric that cannot be gamed in either direction, because it penalizes both directions. It is also the metric that makes the throughput/latency tradeoff *visible as a curve* rather than as two numbers a reader has to reconcile.

### The SLO, declared in advance

An SLO chosen after seeing results is not an SLO. Declared here, before measurement, subject to one revision after a calibration run — and if revised, both the original and the revision are published with the reason.

```
A request meets the SLO iff:
    TTFT      <  [TBD_ttft] ms
AND p95 ITL   <  [TBD_itl]  ms   (computed within that single request)
AND the request completed (not dropped, not timed out, not errored)
```

**Placeholders are deliberate.** They will be set from a calibration run against the *unloaded batch-1 engine* on the target GPU, using a stated multiple of unloaded performance (e.g. TTFT budget = k× unloaded TTFT), so the SLO is anchored to something physical rather than to a round number. The engine's unloaded reference points on A100: ITL p50 ~12.5–12.6 ms and p99 ~12.8–13.2 ms at ~79 tok/s (`BENCHMARKS.md:37-39`), or ~16.1–16.8 ms at ~60–62 tok/s in the later sessions (`BENCHMARKS.md:139-140`) — **and those two sessions are not comparable to each other** (`BENCHMARKS.md:17`: node contention and clocks vary). The calibration run must therefore be taken in the same allocation as the results it anchors.

### Reporting form

The headline result is a **curve, not a point**: goodput (y) versus offered load (x), with the SLO-violation fraction on a secondary axis. Three regions must be visible and named:

1. **Below capacity** — goodput tracks offered load, near-100% SLO attainment.
2. **The knee** — goodput plateaus, SLO attainment starts falling. This is the system's capacity, and it is the number worth quoting.
3. **Above capacity** — goodput *falls* while offered load rises (queueing collapse), or is held flat by load shedding, which is the entire argument for having load shedding.

A single goodput number without the curve it came from is not publishable in this project.

## 4. Workload design

A benchmark's workload is a claim about reality. Stating the distribution is not optional; picking a convenient one and not saying so is how projects get caught.

### Arrival process

**Poisson arrivals** (exponentially distributed inter-arrival times) at rate λ, as the default. Rationale: it is the standard memoryless model, it produces genuine bursts rather than the artificial smoothness of fixed-interval arrivals, and its burstiness is what stresses admission control and queueing — which is what this project is measuring.

A **fixed-rate (deterministic) arrival** mode is also implemented, because comparing Poisson against deterministic at the same mean rate isolates *burstiness* from *load*, and the gap between them is a real result about the scheduler.

Seeded and reproducible. The seed is recorded in every artifact.

### Prompt and output length distributions

Length distributions drive everything — memory pressure, batch composition, prefill/decode ratio, preemption rate. A benchmark using uniform 128-token prompts and uniform 128-token outputs has removed every interesting phenomenon it claims to study.

Commitments:
- **Lengths are drawn from a skewed distribution, not fixed.** Real serving traffic has long-tailed prompts and outputs. The exact distribution family and parameters are recorded per-workload and published with the results.
- **At least one workload has heavy-tailed output lengths**, because a single very long generation holding blocks while short requests queue behind it is the exact scenario that motivates preemption and fairness, and a workload without it makes preemption look unnecessary.
- **Output length is controlled, not model-determined**, for benchmark runs — `max_tokens` is set per request from the distribution and EOS is suppressed or the run accounts for early stops explicitly. Otherwise output length becomes a function of the model's whims and the workload is not reproducible across configurations.
- **Sourcing prompts from a real dataset is preferred over synthetic token noise**, and if synthetic prompts are used, that is stated prominently — the engine already learned this lesson the hard way (`CLAIMS_AUDIT.md:287`: an eval file named `wikitext_sample.txt` that was not WikiText, called *"highest severity in the repo"*).

### Prefix-sharing structure — the load-bearing one

Every claim about the radix prefix cache (G4) and about prefix-aware routing (G5) is a claim about a *prefix-sharing distribution*. If that distribution is chosen to flatter the system, the result is worthless.

Therefore the prefix structure is an explicit, swept parameter, with at minimum:

- **Zero sharing** — every request has a unique prefix. The cache must show ~0% hit rate and must impose *near-zero overhead*. This is the control, and it is also the honest floor: if the cache costs measurable latency here, that cost is published.
- **Realistic system-prompt sharing** — a small set of shared prefixes (a system prompt, a few-shot preamble) with unique suffixes. This is the common production shape.
- **Deep conversational sharing** — multi-turn conversations where turn *n* shares the entire history of turn *n−1*. This is the shape that most favors a radix cache, and it is labeled as such.
- **Adversarial / near-miss sharing** — prefixes that share a long common region and then diverge, with the divergence point straddling block boundaries. This exercises partial hits, block-boundary handling, and copy-on-write, and it is where implementation bugs live.

Sharing rate is a swept parameter, and results are reported **as a function of sharing rate**, never at a single favorable point.

### Warmup and steady state

- **Warmup requests are issued and discarded**, sufficient to load weights, trigger CUDA context creation, compile/autotune any kernel that autotunes, and fill the cache to a representative state. Warmup count is recorded.
- **The measurement window is the steady-state region only.** Ramp-up (queue filling from empty) and drain (queue emptying at the end) are excluded, and the exclusion boundaries are recorded per run. Including the drain tail is a way to accidentally publish a better p99 than the system has.
- **Steady state is verified, not assumed** — queue depth and in-flight request count must be stationary over the window. If they trend, the run is not at steady state and is either extended or discarded. **[inference]** Above the knee, steady state does not exist by definition (the queue grows without bound); those runs are measured over a fixed window and explicitly labeled *unsaturated-window measurement*, not *steady state*.

## 5. Statistics

- **Percentiles are pooled across all requests in the measurement window**, not averaged across per-run percentiles. The engine's harness computes p50/p99 *per run* and stores only the percentiles, discarding the raw samples (`bench/harness.py:136-137,178`) — which makes correct pooling impossible after the fact. **This project stores raw per-request and per-token samples**, and computes percentiles at analysis time.
- **Sample count is reported alongside every percentile.** A p99 over 127 samples is interpolated between the top two values and carries roughly one sample of resolution — that is the engine's situation at `--max-tokens 128` with NumPy's linear-interpolation default (`bench/harness.py:50-51`). A p99 claim requires enough samples to mean something; the minimum sample count for each published percentile is stated.
- **Percentile method is stated explicitly** (interpolation rule), because different tools disagree and the difference is visible in the tail.
- **Multiple independent repetitions per configuration**, with dispersion reported. A single run's p99 is not a result. Where repetitions disagree beyond a stated threshold, that is reported rather than averaged away.
- **Cross-session comparisons are forbidden by default.** The engine documents why: interactive A100 nodes vary in contention and clocks, and its own absolute throughput moved from ~79 to ~60 tok/s across nodes for identical code (`BENCHMARKS.md:17`, `docs/PACE_RUNBOOK.md:161`). **Every A/B comparison in this project runs back-to-back in a single Slurm allocation**, and the allocation/node identity is recorded in the artifact. A comparison that cannot be run back-to-back is reported as two separate absolute measurements, not as a delta.
- **GPU timing must not depend on an accidental synchronization.** The engine's host-clock timings are only valid because `engine/model_gpu.py:158` copies logits to host every step, forcing a sync (`BENCHMARKS.md:60`). A batched serving path may legitimately remove that per-token host copy for performance — at which point host-side `perf_counter` timings would silently become measurements of queue-submission time rather than execution time. **Server-side GPU timings use CUDA events or an explicit sync at a declared point.** Client-side timings are host-clock but measure real network-observable behavior, which is what they should measure.

## 6. Baselines

A result is a comparison. Each of these is defined precisely enough to be reimplemented by a skeptic.

**B1 — The unmodified engine, batch 1, over HTTP.** The floor. Establishes what the serving layer is worth. Note that this requires the engine's server to reach the GPU path, which it currently cannot (`engine/server.py:24-30` loads the CPU NumPy model) — so B1 is either measured against a serving-layer configuration with batching and paging disabled, or against a patched engine server, and **which one is used is stated**. Preference: serving layer with features disabled, so the HTTP stack is held constant and only the scheduler differs.

**B2 — Static batching.** Fixed batch size, batch runs to completion before the next is admitted. This is the honest thing continuous batching is compared against, and the comparison is meaningful because the difference is *entirely* scheduling — same kernels, same memory manager. Under skewed output lengths, static batching wastes the slots of finished sequences waiting for the longest one; that waste is exactly the continuous-batching claim, and it should be shown as a GPU-utilization or slot-occupancy measurement, not just as a throughput delta.

**B3 — Contiguous per-sequence KV allocation.** The engine's current behavior (`engine/scheduler.py:26-27`, `max_seq=2048` per request). The paged-cache claim (G1/S1) is a capacity claim against this, at fixed VRAM.

**B4 — Round-robin routing.** Defined precisely: *requests are assigned to replicas in strict rotation, independent of replica load, queue depth, or cache state; no re-routing after assignment.* This is a genuinely weak baseline and must be labeled as such — beating round-robin is table stakes, not a result.

**B5 — Least-outstanding-requests routing.** *Assign to the replica with the fewest in-flight requests; ties broken by rotation.* This is the real baseline. It is load-aware but cache-blind, so the delta between B5 and prefix-aware routing isolates **exactly the value of cache awareness** — which is the actual claim. A prefix-aware router that beats B4 but not B5 has demonstrated load balancing, not prefix awareness, and that result must be published as such if it occurs.

**B6 — vLLM.** Handled separately in §8, because fairness is not assumable.

## 7. Cache hit rate instrumentation

Measured at **block granularity**, server-side, because that is the granularity at which the allocator actually saves work:

```
hit_rate = blocks_reused_from_cache / blocks_required_for_prefill
```

Reported per request and aggregated. Also instrumented: partial-hit depth (how many blocks matched before divergence), radix tree node count and depth, eviction count, and blocks held by reference count > 1 (i.e. genuinely shared).

**A hit rate without the workload's sharing distribution attached is not a number.** Every hit-rate figure in this project is published adjacent to the sharing structure that produced it (§4). A 90% hit rate on a deep-conversational workload and a 5% hit rate on a zero-sharing workload are both correct and neither means anything alone.

**Overhead must be measured, not assumed.** The zero-sharing workload exists to answer *"what does the cache cost when it never helps?"* — radix tree insertion, lookup, and refcount bookkeeping on every request, for zero benefit. If that cost is material, it is published as a negative result, and it becomes an argument for making the cache adaptive.

## 8. Can a vLLM comparison be made fair?

**[inference]** Probably not on absolute throughput, and this document commits to that position in advance rather than discovering it mid-benchmark and quietly dropping the comparison.

The confounds:

- **Kernels.** vLLM ships fused, tuned kernels across the whole forward pass. This project's forward pass is the engine's — hand-written PyTorch ops (`engine/components_gpu.py`) whose linear layers are plain `x @ w.T` (`:24`), against an engine that already measures ~5× slower than llama.cpp at batch 1 (`BENCHMARKS.md:31`). Any throughput comparison is dominated by kernel quality, which is not what this project is about.
- **Runtime.** CUDA graphs, custom allocators, prefix-cache implementation details, tokenizer path, and continuous-batching heuristics all differ.
- **Configuration surface.** vLLM has many knobs whose defaults are tuned; a comparison against defaults measures tuning effort, not design.

**What a fair comparison would require:** holding the forward pass constant, which is impossible across two different engines.

**Therefore the commitment:**

1. **Do not publish "we beat vLLM" or "we are X% of vLLM" as a throughput claim.** It would be dishonest in either direction — flattering if the workload favors this system, self-flagellating if it doesn't, and uninformative either way.
2. **Do publish vLLM as a *scaling-shape* reference where the shapes are comparable.** Example: does goodput-vs-offered-load show a knee in the same place relative to each system's own batch-1 capacity? Does cache hit rate as a function of sharing rate follow the same curve? These are *design* comparisons, and they are legitimate because they normalize away kernel quality.
3. **Do use vLLM as a correctness and sanity reference** — if this system's hit rate at a given sharing rate is wildly different from vLLM's on the same workload, one of them has a bug, and finding out which is valuable regardless of the answer.
4. **If even the shape comparison proves unfair, say so and drop it**, in writing, with the reason. That is a stronger settled answer than a comparison table: *"I tried to benchmark against vLLM, here is specifically why the comparison isn't meaningful, and here is what I compared instead."*

## 10. When should prefix-aware routing be expected to LOSE?

Answered before benchmarking, and published alongside the wins. A router that is only ever shown winning has been benchmarked on a workload chosen to make it win.

Prefix-aware routing should be expected to lose — or at best tie — under:

1. **Zero or near-zero prefix sharing.** Nothing to be cache-aware about. The router pays lookup and bookkeeping cost for no benefit, and any deviation from load-optimal placement is pure loss. Expected: ties B5, loses slightly if the policy sacrifices any load balance.

2. **Uniformly shared prefixes** — when *every* request shares the *same* prefix. Then every replica caches it after warmup, cache state is identical everywhere, and prefix awareness degenerates to "pick any replica." B5 wins on load balance alone. **This is important because it is the naive mental model of prefix caching**, and it is the case where the fancy router is worthless.

3. **High load near or above capacity.** Cache affinity and load balance conflict directly: the replica holding the right prefix is often the replica that is already busy *because* it holds the popular prefix. Routing for affinity concentrates load; routing for balance destroys affinity. Near saturation, queueing delay dominates prefill savings, and a cache-blind load-balancer wins. **Expected result: prefix-aware routing wins at low-to-moderate load and loses above the knee unless the policy explicitly blends affinity with load.** Publishing the crossover point is a better result than publishing a win.

4. **Short prompts.** The saving is prefill work avoided. If prompts are short, prefill is cheap, and there is little to save — while the routing cost and the load imbalance are unchanged. Expected: benefit shrinks toward zero as prompt length shrinks; there is a prompt length below which the policy is net negative.

5. **High replica-cache turnover.** If working-set size greatly exceeds aggregate cache capacity, entries are evicted before reuse. Routing to "the replica that had it" finds it gone. Degenerates to worse-than-random placement, because the affinity signal is stale.

6. **Very few replicas.** At N=2 there is little routing freedom; at N=1 the policy is a no-op and only the local radix cache matters. Benefit should be expected to grow with N, and the measurement should show that growth or explain its absence.

7. **Highly skewed prefix popularity.** A single very hot prefix creates a hotspot: affinity routing sends a disproportionate share of traffic to whichever replica owns it. Without load-aware blending or replication of hot prefixes, this is a self-inflicted imbalance. **[inference]** This is the most likely place for a genuinely bad result, and therefore the most valuable one to measure.

**Commitment:** at least cases 1, 2, 3, and 7 are measured and published whether or not they are flattering. A results table containing only wins is evidence of workload selection, and a reader who knows this field will assume exactly that.

## 11. Reporting negative results

Rules, adopted from what the engine got right and extended:

1. **Publish the losing row.** The engine publishes that its kernel is 39% slower than SDPA at kv_seq=128 and states why it kept the row: *"omitting it would make the kernel look uniformly competitive when it is not"* (`BENCHMARKS.md:94`). Same standard here.
2. **Name what was not measured.** `BENCHMARKS.md:151` — *"The split between the two causes has not been measured."* Unmeasured splits are stated, not implied away.
3. **Maintain a known-gaps section**, in the style of `BENCHMARKS.md:243-250`, written by the author before a reader finds the gap.
4. **Commit the artifacts.** `results/` is tracked in git, as the engine already does (24 files under `bench/results/`, `.gitignore:29`). Every published number resolves to a committed file containing the raw samples, the config, the seed, the workload parameters, the git SHA of this repo, the pinned engine tag, and the Slurm allocation identity **and QOS**.
5. **Superseded numbers stay visible.** When a number is corrected, both versions and the reason remain in the document — as the engine does for its perplexity figure, superseding +0.14 with +0.044 and explaining that the earlier eval text was not WikiText (`BENCHMARKS.md:191-198`). Silently replacing a number is indistinguishable from hiding one.
6. **A claim whose artifact cannot be regenerated is deleted, not softened.**

## 12. Threats to validity — the silent ones

These are the failure modes that produce a *plausible wrong number* rather than an obvious error. Each is owed a detection mechanism in the risk register.

| Threat | Why it is silent | Detection |
|---|---|---|
| **Coordinated omission** in the load generator | Saturated system reports excellent latency; nothing errors | Track intended-vs-actual dispatch drift; invalidate the run above a threshold |
| **Host-clock timing without GPU sync** | Measures queue submission, not execution; numbers are plausibly fast | CUDA events server-side; assert a sync point exists on the timed path |
| **Measurement window including drain** | p99 improves as the queue empties at the end | Explicit window boundaries recorded per run; stationarity check on queue depth |
| **Cross-session A/B** | Node contention shifts absolute numbers ~25% for identical code (`BENCHMARKS.md:17`) | Allocation id in every artifact; comparisons refuse to render across allocations |
| **Prefix-cache correctness bug producing wrong tokens** | Faster *and* wrong; throughput looks great | Output equality gate: greedy output with cache on must be bit-identical to cache off, per request, run every benchmark |
| **Preemption dropping or duplicating tokens** | Rare, load-dependent, invisible in aggregate metrics | Same equality gate under forced memory pressure; per-request token accounting |
| **Workload silently degenerate** | Length or sharing distribution collapses to near-constant; benchmark measures nothing | Publish realized distributions from each run, not just requested parameters |
| **Column-name collisions across harnesses** | Two different quantities under one name — the engine's known gap #1 (`BENCHMARKS.md:247`) | Unambiguous metric names; unit and source recorded in the schema |
| **Batched output diverging from single-sequence output** | Only shows under specific batch compositions; correctness tests use batch 1 | Batch-invariance test: same prompt, alone vs in a mixed batch, bit-identical greedy output |

The last one deserves emphasis. **The engine has no model-level GPU correctness oracle at all** — `tests/test_gpu_model.py:42-45` asserts only that outputs are finite, correctly shaped, and have an in-range argmax; GPU fp16 tokens are never compared to HuggingFace or to the CPU reference path. Every correctness claim in the engine (`tests/test_forward.py:113,137`, `tests/test_decode.py:30-48`) is against the **CPU fp32** path. Building a batched, paged, preemptible scheduler on top of a forward pass with no output-level oracle means any divergence is unattributable — it could be the allocator, the batching, the paged attention, or the pre-existing GPU path. **That oracle is Tier 0 in the PRD (§5) and is a prerequisite for every benchmark in this document.**
